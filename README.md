# ارفا — لوحة الإدارة

واجهة ويب خفيفة لإدارة متاجر ارفا: الطلبات، الكتالوج، الأسئلة المعلّقة، التصعيدات، وحالة المتاجر.
Next.js 14 (App Router) + TypeScript + Tailwind، عربية RTL بالكامل، جاهزة للنشر على Vercel.

## النشر على Vercel

1. ارفع المجلّد لمستودع Git.
2. Vercel → New Project → اختر المستودع (يُكتشف Next.js تلقائياً).
3. أضف متغيّرات البيئة:

| المتغير | القيمة |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | رابط Supabase العام، مثل `https://supabase.7azgroup.com` |
| `SUPABASE_SERVICE_ROLE_KEY` | مفتاح service_role من `.env` الخاص بـ Supabase |
| `ADMIN_PASSWORD` | كلمة مرور تختارها لهذه اللوحة |
| `SESSION_SECRET` | أي نص عشوائي طويل |

4. Deploy.

> Vercel يتّصل بـ Supabase عبر الرابط العام (Cloudflare Tunnel)، لا عبر شبكة Docker الداخلية.
> تأكّد أن `supabase.<نطاقك>` يستجيب من خارج السيرفر.

## محلياً

```bash
cp .env.example .env.local   # ثم املأ القيم
npm install
npm run dev
```

## ما تفعله الصفحات

| الصفحة | تفعل |
|---|---|
| نظرة عامة | شريط «ما ينتظرك»، ثم إيرادات وطلبات ونسبة رفض آخر 30 يوماً |
| الطلبات | قائمة ومرشّحات وبحث بالهاتف، وصفحة تفصيل بمسار الحالة من `order_status_log` |
| أسئلة معلّقة | `pending_followups` — فجوات معرفة البوت، مفتوحة ومُجابة |
| تصعيدات | محادثات مكتومة، مع الوقت المتبقّي لفكّ الكتم التلقائي |
| الكتالوج | تعديل السعر والمخزون والوصف — يقرأه البوت حيّاً |
| المتاجر | حالة الاشتراك والموديل ومعرّف المدير |

## قواعد محفوظة عمداً بالكود

- **`orders.total_amount` لا يُكتب أبداً.** trigger بقاعدة البيانات يحسبه من `order_items`. الصفحة تعرضه فقط.
- **اسم المنتج لا يُعدَّل من الكتالوج.** إعادة التسمية طريقة للالتفاف على حدّ عدد العناصر بالباقة، فالتصميم يمرّرها عبر قناة الإدخال المُدارة.
- **تأكيد الطلبات ورفضها يبقى ببوت المدير.** الزر بتيليجرام يُخبر الزبون ويسجّل الانتقال؛ صفحة الطلب للعرض والمراجعة.
- **الكتالوج يُقرأ حيّاً.** لا «تدريب» ولا إعادة نشر — تحفظ سعراً، فالزبون التالي يسمعه.

## الأمان — اقرأ هذا قبل أن يدخل أصحاب المتاجر

النسخة الحالية **لمشغّل المنصّة فقط**: كلمة مرور واحدة مشتركة، وكل الاستعلامات تعمل على الخادم
بمفتاح `service_role` الذي يتجاوز RLS كلياً. المفتاح لا يصل للمتصفّح إطلاقاً (يُستورد فقط داخل
server components و server actions)، لكن من يدخل باللوحة يرى كل المتاجر.

هذا مقبول لتجربة يستخدمها شخص واحد. **غير مقبول لحظة يدخل أول صاحب متجر.** قبل ذلك:

1. فعّل Supabase Auth، وأنشئ جدول `store_users` يربط `auth.users.id` بـ `store_id` ودور.
2. اكتب سياسات RLS: المستخدم يقرأ ويكتب صفاً فقط إذا كان `store_id` ضمن متاجره.
3. بدّل `db()` إلى anon key + جلسة المستخدم. أبقِ `service_role` لعمليات المشغّل عبر المنصّة فقط.
4. اختبر أن متجر «أ» لا يقدر يقرأ طلبات متجر «ب».

RLS مفعّلة أصلاً على كل الجداول عدا `plans`، لكن لم تُكتب لها سياسات لمسار مستخدم عادي بعد — هذا بالضبط ما تُركت لأجله.

## غير مبني بعد

- تسجيل دخول لكل متجر (أعلاه)
- إشعار الزبائن المنتظرين عند عودة منتج نافذ (`pending_followups` بنوع `product_availability`)
- معالج صفحات لأزرار بوت المدير — بوت المدير نفسه غير مبني بعد
- رفع الصور إلى Supabase Storage
